The naked machine

CPU · von Neumann · cache · fetch-decode-execute · jumps · stack and indirection · x86 Assembly
Guillermo · Exit criterion met on 2026-10-04 · Phase closed
The conceptual leap of the phase Finiteness. The CPU's real workspace is finite, named and very small: 16 slots. Every operation costs cycles, every piece of data has to travel, and the distance at which data lives determines the cost of using it. This is what has no analogue in abstract mathematics.

§ 1.1Three units and a clock

A CPU is a small set of units coordinated by a clock. The three that matter:

  • ALU executes arithmetic and Boolean operations. It is binary by construction: two operands, one result.
  • Registers internal memory, fixed in number and in size. The only thing the ALU operates on directly.
  • Control Unit reads each instruction from memory, decodes it and activates the control lines.
In the workshop The Master Builder (Control Unit) does not touch the wood: it reads the order, deciphers it and shouts to the craftsman what to do. The Carpenter (ALU) is pure transforming force: it takes the two planks on the bench, performs the operation it was ordered to and leaves the result on the bench. Together they are «the carpenter» in the simple version; the whole workshop is the CPU.
Structural point
The Control Unit is not programmable

It stores no instructions and runs no program of its own: it is a circuit, a finite automaton made from the gates of Phase 0. Given a bit pattern it activates some lines or others. Reprogramming it would mean redesigning the chip.

It is the transition function δ of the Turing Machine made into hardware. Universality is obtained by changing the tape, not the machine.

§ 1.2The bench and the shelves

A register is exactly one word: 8 bytes on 64 bits. x86-64 has 16 general-purpose ones (rax, rbx, rcx, rdx, rsi, rdi, rbp, rsp, r8…r15): 16 × 8 = 128 bytes of truly immediate workspace.

Word width varies with the architecture: x86-32 had 8 registers of 32 bits; ARMv8 has 31 of 64; an AVR microcontroller, 32 of 1 byte. Word width = register width = address width: the three move together by design.

A register and a variable are not the same

The register is the container: fixed, one word. The variable can be smaller: a 1-byte character takes an 8-byte register and leaves 7 unused. If it is larger than the word, it does not fit: the operation is split into several instructions that propagate the carry by hand (the atomicity of Phase 0).

§ 2.1Instructions and data share memory

Instructions do not live in the CPU: they live in memory, in the same addressable space as data. Everything is bytes; the difference between «instruction» and «data» is one of interpretation, not location. That is the von Neumann architecture, and it is that of practically every PC, phone or server.

The alternative, Harvard, separates memories for code and data; it survives in microcontrollers. Inside the CPU, the L1 cache is indeed split into L1i and L1d: von Neumann on the outside, Harvard on the inside.

Structural consequence
Everything depends on where the finger lands

If nothing in the bytes distinguishes code from data, a program's correctness depends on the flow never landing where it should not. Almost all binary exploitation is making rip land somewhere unforeseen.

§ 2.2Who writes the sheet?

Scenario 1: you write a program (a password manager)
What you write in C or Python is not yet the sheet: it is a draft in a language the carpenter does not read. The compiler translates it into machine bytes; that is the sheet. In Python there is no ahead-of-time compilation: the sheet is the interpreter, and your script is just one more piece the interpreter reads.
Scenario 2: you open Spotify and play a song
The sheet already exists: the executable, stored on disk. When you open it, the operating system copies it from disk to RAM and puts the finger on its first line. The song is not a sheet: it is a piece. The disk is a distant warehouse: nothing runs from there.

What they have in common: the carpenter always reads machine bytes in RAM. All that changes is who wrote the sheet and when. And the operating system is a sheet too: the one that decides which other sheets get read (Phase 3).

§ 2.3Where does each thing live?

  • Storeroom (RAM) sheet and pieces mixed together, indistinguishable. The Lego analogy: the sheet is the manual, the pieces are the bricks.
  • Ledge (cache) both; L1 separates them (L1i for the sheet, L1d for the pieces); L2 and L3 are mixed.
  • Bench (registers) only pieces. The sheet is never put on the bench.
Careful with rip rip does not hold the instruction: it holds its address. It is the finger, not the line. The line being executed is held by the carpenter's hand (the IR), private circuitry that is not one of the 16 slots.
Correction to your synthesis The carpenter is not the pointer. The carpenter is the working CPU (CU + ALU); the pointer is its finger on the sheet, rip. The carpenter uses the finger; it is not the finger.

§ 3.1The physical tension

Small-and-fast and large-and-slow are in irreducible tension. An instantaneous memory has to be tiny; one that holds billions of cells takes up space and is therefore far away.

§ 3.2Locality: the bet

  • Temporal what was used recently will be used again soon. Passive: the data stays on the ledge.
  • Spatial what is next to what was used will be used soon. Active and speculative: data nobody asked for is brought up.

Loops justify the bet: ten instructions repeated a million times are fetched once and stay. It is not a law, it is an empirical regularity: a program that jumps at random is legal and ruins the cache.

§ 3.3The trip to the storeroom

The cache never fetches a single byte: it fetches a contiguous block of 64 bytes, the cache line. The expensive part is going, not carrying: if you already walked all the way there, fill your arms.

  1. Bring the neighbours (cache line): happens on every trip. Automatic and blind. It is not prediction: the block is the minimum unit of transport.
  2. Get ahead (prefetch): the CPU notices you are reading in order and has the next stretches fetched before they are needed. This is prediction, and it can fail.
Exercise 3.2
What does the cache bring when it goes to memory, and why?
See answer

A contiguous block of 64 bytes, not the requested byte. The dominant cost is the trip, not the volume; and spatial locality bets that the neighbours will be requested soon.

Practical consequence An array traversed in order makes use of each line several times; traversed in large strides, it causes one trip per access. Same algorithm, same number of operations, up to 10 times slower. Asymptotic cost does not see it. Security seed: if timing depends on what was in the cache, timing leaks information (side channels).

§ 4.1The four steps, in the workshop

  1. Fetch. The carpenter looks at where its finger points (rip) and brings that line, almost always from the L1i ledge; if not, a trip to the storeroom and back with 64 bytes. It holds it in its hand (IR).
  2. Decode, read. The Master understands two things at once: which verb it is and how long the line is.
  3. Execute, do. One place is modified: mov → a piece on the bench; cmp → the notebook; jmp/je → the finger.
  4. Advance. The length of the line is added to the finger, unless the verb already moved it: that is where the jump is.

And back to 1, billions of times per second. The CPU does not see the program: it sees one instruction, executes it and looks at the next.

§ 4.3Variable length: a prefix code

In x86 instructions are 1 to 15 bytes long, with no separators. The length is implicit in the opcode: after decoding the first bytes, the circuit already knows how many more belong to it.

In your language It is a prefix code: no valid opcode is a prefix of another, so the bit stream is parsed unambiguously and without delimiters, as long as you enter at a correct starting point.

§ 5.1The unconditional jump

A jump writes an address directly into rip instead of letting the length be added to it. The destination is encoded in the instruction itself.

There are no loops in hardware
Just a finger that goes backwards

A loop is just a rip that had an earlier address written into it. The structure is seen by the programmer; the carpenter only knows that sometimes the finger goes back.

§ 5.2The notebook and the conditional jump

The ALU leaves marks in rflags about its last calculation: was it zero? (ZF), carry? (CF), negative? (SF), signed overflow? (OF).

  • cmp a, b subtracts a − b and discards the result: it only leaves the marks. Equal ⇒ result is zero ⇒ ZF = 1.
  • je target looks at the notebook. If ZF = 1, it writes the target into rip; if ZF = 0, it does nothing and the finger moves down.
Where the confusion concentrated They are three different pieces: je is the order; the target is a line written in the instruction; ZF is the condition, which lives in the notebook and is not a target. There are two possible targets —the written one and the next line— and a single question that decides.

The division of labour: the ALU judges, rflags remembers the verdict, the jump obeys it.

§ 5.3Misaligned instructions

Since the length is only known when decoding and there is no start marker, the CPU cannot detect that it is reading from the middle of an instruction.

Exercise 5.1
What happens if rip lands in the middle of an instruction?
See answer
Your initial answerThat the processor would detect the misalignment and recover. It is the natural intuition, and it is exactly the one the hardware does not fulfil.

It does not stop or warn. It decodes that byte as an opcode, executes whatever it means, advances by that length and carries on: a different program, made of instructions nobody wrote. The instruction is not a property of the bytes, but of the bytes plus the point where reading started.

It is a real offensive technique: hiding instructions inside others. On fixed-length architectures (ARM, RISC-V: 4 bytes) it is impossible, because there is only one valid alignment.

Seed of Phase 2
The return address is not verified

It sits on the stack, mixed with data the program writes. If badly measured data is written beyond its space and on top of it, the likely outcome is an invalid jump and the end of the program. If instead of garbage a chosen address is written, the program returns wherever the attacker decided: buffer overflow.

§ 6.3The address is a number

Memory is a sequence of 1-byte cells; an address is the number of the cell. Formally:

f : D → {0,1}⁸, D ⊂ ℕ finite

The critical part: an address is a natural number, so it fits in a register like any data. You can put the number of a cell on the bench instead of its contents.

§ 6.4Indirection: F(F(x))

A 64-bit address does not fit in a byte, so a whole word is read:

F(x) = ⟨ f(x), f(x+1), …, f(x+7) ⟩ as a natural number, F : D → ℕ

Now the types match and F(F(x)) is well defined: two chained reads. If cell 200 contains 7000 and cell 7000 contains 42, then F(200) = 7000 and F(F(200)) = 42. Cell 200 does not hold the data: it holds where it is.

Nothing in the bytes distinguishes a data number from an address number: the interpretation is supplied by the program. A pointer is a number someone decided to use as an index instead of as a value.

Exercise 6.2
What do you gain by keeping the address of some data in a register instead of the data itself?
See answer
  • The reference fits even if the object does not: an address takes one word, whatever the size of what it points to.
  • Sharing without copying: two parts with the same address see the same data.
  • Linked structures: if each element keeps the address of the next, you get lists, trees and graphs. What mathematics defines through relations, here is built with addresses.

§ 7.1Syntax and brackets

verb destination, source

The first operand is where the result goes: mov rax, 5 puts 5 in rax; sub rax, rbx computes rax = rax − rbx.

  • rax the register; its contents are used as a value.
  • [rax] the cell whose address is in rax: the composition F(F(x)) turned into notation.

The side of the bracket decides the direction: mov rbx, [rax] reads from memory; mov [rax], rbx writes. Same verb, inverse operation.
